# Plan 1 — Core Engine + First Vertical Slice — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A publishable CLI that creates a pnpm monorepo (Nx or Turborepo) with any number of Express/NestJS backends and Next.js/React+Vite frontends wired to them over typed REST, with Dockerfiles, docker-compose (Postgres, Redis), validation rules, a manifest, `add app`, non-interactive mode, and a CI matrix that proves every combination builds.

**Architecture:** A single TypeScript package. Input (prompts, flags, or JSON) → `StackConfig` (zod) → rules engine (errors / warnings / auto-fixes) → generation engine that asks plugins for in-memory `FileTree`s and merges them → writer → post-steps. Every framework, service and monorepo tool is a plugin folder under `src/plugins/`, so a contributor adds one by adding a folder. The output is a plain pnpm workspace with `package.json` scripts; Turbo/Nx are a thin config layer on top.

**Tech Stack:** Node 24 LTS, TypeScript, pnpm, commander (CLI args), @clack/prompts (interactive), zod (schemas), vitest (tests), tsdown (build), Biome (lint/format, also used in generated repos), yaml (compose/pnpm-workspace output).

**Spec:** `docs/superpowers/specs/2026-10-17-monorepo-cli-design.md`

## Global Constraints

- Node 24 LTS; TypeScript everywhere (CLI and generated code); ESM for the CLI itself.
- pnpm only (generated repos and the CLI repo).
- Generated repo is a plain pnpm workspace with `package.json` scripts; **no dependency on `@nx/*` generators**. Nx gets `nx` + `nx.json` only.
- Every dependency version written into generated repos comes from one file, `src/versions.ts`, as an **exact** version (no `^`, `~`, `latest`), set at implementation time to the latest stable via `npm view <pkg> version`.
- Official Docker images only; **no Bitnami images, no MinIO, no kafkajs, no Remix v2**.
- Manifest file in generated repos: `.monoplate.json`, field `schemaVersion: 1`.
- CLI name is the placeholder **`monoplate`**, defined once in `src/meta.ts` (`CLI_NAME`); nothing else hard-codes it.
- Generated workspace packages are named `@<projectName>/<pkg>`.
- Tool-owned files (regenerated by `add`): root `package.json` (JSON-merged, user keys kept), `pnpm-workspace.yaml`, `turbo.json`/`nx.json`, `docker-compose.yml`, root `.env.example`, `.monoplate.json`, `packages/*-client/**`, `apps/*/src/generated/**`. Everything else is user-owned and never rewritten by `add`.

## Review Focus

1. **Target directory already exists and is non-empty** → `create` refuses with a clear message and writes nothing (unless `--force`). Test in Task 5.
2. **Bad app names** (uppercase, spaces, leading digit, duplicates, reserved names like `packages`, `node_modules`) → blocking error naming the app. Test in Task 4.
3. **`add app` on a repo with no manifest, or `schemaVersion` ≠ 1** → refuses with a message that says which, and writes nothing. Test in Task 13.
4. **pnpm or git not installed** when post-steps run → generation still succeeds; CLI prints the exact commands to run manually and exits 0. Test in Task 12.
5. **Frontend that uses no backends** → warning (not error), and the frontend still builds with no generated API file imports. Test in Task 4 (warning) and Task 14 (combo `react-vite` with no backend builds).

### Task 4: Rules engine

**Files:**
- Create: `src/rules/index.ts`, `src/rules/rules.ts`
- Test: `tests/rules/rules.test.ts`

**Interfaces:**
- Consumes: `StackConfig`, `Registry`.
- Produces:
  - `interface Issue { rule: string; level: 'error' | 'warning' | 'fix'; message: string; app?: string }`
  - `interface Rule { id: string; check(stack: StackConfig, reg: Registry): { issues: Issue[]; stack?: StackConfig /* fixed stack, for 'fix' */ } }`
  - `validateStack(stack: StackConfig, reg: Registry): { stack: StackConfig; errors: Issue[]; warnings: Issue[]; fixes: Issue[] }` — runs rules in order, threading the fixed stack through.
  - Rules (ids exact): `at-least-one-app`, `app-name-valid`, `framework-known`, `api-style`, `uses-valid`, `frontend-without-backend`, `service-known`, `assign-ports`.

Rule behavior:
- `app-name-valid`: error unless `/^[a-z][a-z0-9-]*$/`, not in `['packages','apps','node_modules','gateway','config','types']`, and unique; also error if project `name` fails the same regex.
- `framework-known`: error if `reg.framework(app.framework, app.kind)` is undefined; message lists valid ids for that kind.
- `api-style`: backend with no `apiStyle` → fix to the plugin's `apiStyles[0]`; with an unsupported one → error listing supported; frontend with `apiStyle` → error.
- `uses-valid`: frontend `uses` must name existing backends (error); backend with non-empty `uses` → error.
- `frontend-without-backend`: warning.
- `assign-ports`: fix; apps without `port` get `plugin.defaultPort`, bumped by 1 until unique among all app ports; explicit duplicate ports → error.

- [ ] **Step 1: Write failing tests** (build a test registry with stub `next` frontend, `express` backend `apiStyles:['rest']`, default ports 3000/4000):
  - names `['Web','web','2x','packages','my app']` → 5 errors from `app-name-valid`, each with `app` set; duplicate `api`,`api` → error.
  - backend missing `apiStyle` → `fixes` contains `api-style`, returned stack has `apiStyle: 'rest'`.
  - `apiStyle: 'graphql'` on express → error mentioning `rest`.
  - frontend `uses: ['nope']` → error from `uses-valid`.
  - frontend with `uses: []` → exactly one warning `frontend-without-backend`, no errors.
  - two express apps, no ports → ports `4000` and `4001`; explicit `port: 4000` twice → error.
  - `apps: []` → error `at-least-one-app`.
- [ ] **Step 2: Run** — FAIL. **Step 3: Implement.** **Step 4: Run** — PASS.
